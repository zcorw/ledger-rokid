# Receipt review workflow

**English** | [简体中文](REVIEW-WORKFLOW.zh-CN.md)

The owner accepted the previous capture/recognition package on 2026-11-17. This increment adds review layout, speech changes, saved drafts and explicitly authorized accounting. Its local tests/package do not establish installation or acceptance on the glasses.

The actual registered capture page contains the review interface. The owner's sketch defines four rows: merchant, amount, date and account, with category to the right of amount. Labels and values share a line. Seven field labels remain visible when values are missing; the three actions stay on one line at the bottom. Merchant text uses the available slot width explicitly, with an 8px trailing gutter, instead of intrinsic single-line sizing. Long merchant names wrap and scroll vertically within that row; other long values scroll horizontally inside bounded slots. Neither displaces other fields/actions. Feedback has its own bounded vertical scroll area. Confirmed currency codes distinguish JPY/CNY and USD/CAD; no currency is inferred from an ambiguous symbol. Temple swipes select bottom actions and head motion selects fields; Enter/tap activates once. Pending financial outcomes lock changes until checked.

Voice edit starts continuous `SpeechRecognition` in the user's activation with interim results enabled. Live text replaces revised interim segments without duplicating cumulative results. A transcript panel replaces the fields while recording/analysis is active; Stop recording and Cancel remain reachable by tap or direction/Enter. The first final segment and silence do not stop capture or send a request. The user must select Stop recording: this calls `stop()` to flush the remaining audio, waits for final text and the end event, then sends the complete transcript/current fields to the correction endpoint. Only this finalization wait has a timeout (10 seconds); active listening has no app timer. An unexpected end, remaining interim text, empty/oversized text or errors retain visible text and leave the bill unchanged, without silently submitting a partial sentence. Cancel/hide/exit abort capture or inference and ignore late events; overlapping key/tap events cannot turn Start into Stop or Cancel into Draft. Final text remains visible with the outcome until retake/hide/exit, in memory only; audio/transcripts are not logged or persisted locally. Missing runtime support or permission errors preserve the candidate and offer the website as an alternative. The backend model cannot save or submit financial entries. Corrected field labels and warnings are shown. Account names must match one owned active account; ambiguous names are not guessed.

Temple swipes select only the bottom actions; head movement selects the seven fields in their displayed rows and columns (merchant; amount/category; date/currency; account/note). Each area remembers its own focus. The first swipe from a field restores the previous action without advancing it; the first head motion from the actions restores the previous field without moving it. Further inputs navigate within that area, with field edges clamped and no row wrap. Click/Enter edits the current field. The [official orientation sensor](https://open.rokid.com/aiui/api/device/absolute-orientation-sensor?lang=en-US&version=0.19.0) supplies relative pose readings: after 250ms at a quiet pose, a deliberate 12-degree tilt/turn held for 120ms moves once, and a 150ms return to the 5-degree neutral band rearms it. Holding a turn does not repeat; small, brief or diagonal motions are ignored. Sensor availability, mounting-axis direction and thresholds require real-glasses acceptance; unsupported hosts show a message while buttons remain usable. Sensing stops during hidden/unloaded, whole-bill speech and locked financial states. The field voice view keeps the current value, live text and every legal choice in four columns; twelve categories fit compact cards, and head Up/Down scrolls longer lists in the same page. Swipes choose Stop/Retry or Cancel, Enter activates, and Back cancels. Editing or canceling returns to the remembered field without overwriting the remembered bottom action. Ambiguous speech keeps the choices and original value. Account ID/name form one logical field; the Voice edit button retains whole-bill correction.

Head-input diagnosis uses the [page-owned world-awareness API](https://open.rokid.com/aiui/api/framework/page?lang=en-US&version=0.19.0) first, with the standalone orientation sensor as a compatibility fallback. A rendered-bill callback starts sensing after state is applied. Readings accept the documented event quaternion or x/y/z/w payload as well as the instance property. Visible status distinguishes waiting for data, quiet-pose calibration, ready with relative pitch/yaw, return to neutral, unavailable, invalid or interrupted data. No valid first reading or a stalled stream is reported after 3 seconds instead of waiting silently. Status updates are limited to twice a second while the state stays the same; timers/listeners are removed on stop, and late events are ignored. Voice-view failures reuse the instruction line so twelve choices still fit. This improves startup compatibility and observability; the reported 1.2.3 hardware failure has not yet been attributed to a confirmed sensor, runtime or threshold cause, and real-glasses acceptance is still required.

The paired backend adds `GET /review-options` (version 1; complete categories, enabled currencies and active owned accounts) and optional `targetField` on `POST /review-correction`. Scoped replies add `fieldOutcome`: `matched`, `unchanged`, `ambiguous` or `unmatched`. Client/server both enforce the field boundary. Enumerated fields use exact normalized labels/aliases, unique contained names, then conservative text similarity (at least 0.72 with a 0.15 lead); close competitors/negations require clarification. This is not general phonetic/semantic matching. Free fields use the existing model with an explicit target; other returned fields are discarded. There are no financial writes. Choices stay in memory and clear on hide/exit. Deploy this backend increment before installing the native package; unavailable/invalid choices fail explicitly. Existing requests without a target retain their earlier behavior.

Draft saves the current fields on the existing original receipt. Stable operation keys and optimistic versions protect retries/stale edits. A lost save response is queried. A failed save retains the candidate. The website's Recognized receipts page can filter/search drafts, show the original, edit fields and explicitly create a linked expense. Original OCR fields and original image bytes are preserved separately from the corrected draft.

Confirm requires amount, date, ISO currency, category and account. If accounting is not enabled, the glasses display the phone device-authorization link. Opening it does not authorize anything: the signed-in owner must select the exact device, read the warning, check the acknowledgement and approve. Revocation of accounting does not revoke receipt recognition/draft access. Ordinary asset/administrative APIs remain inaccessible to the device token.

The confirmed draft revision is submitted through the existing verified submission state machine and backend expense writer. An existing linked expense is returned instead of recreated; deleted-record tombstones remain effective. A possible duplicate requests a second explicit activation. Permission checks, draft saving and submission are mutually exclusive with editing. Cancel/hide/exit invalidates late results and preserves financial uncertainty.

Before a financial request, Agent-isolated storage receives only `{version, resource, receiptId, revision, requestKey}`. It contains no image, field values, transcript or provider key. A storage error prevents sending. Restart recovery first queries the server outcome; a committed expense needs no new POST. An uncommitted operation loads the server draft and waits for explicit confirmation to reuse the same key. A changed draft is shown for fresh review. After success, Continue capture starts a new receipt.

Deploy the paired website/backend through migrations `0014_receipt_drafts` and `0015_device_expense_grants`, then install this resource package. Do not auto-enable accounting on existing grants. Use `npm run check`, `npm test` and `node qa/review-layout.mjs` for local checks (`REVIEW_CHROMIUM_PATH` may select an installed Chromium browser). Tests use synthetic data and mocked speech/model replies.

The old amount-first screen and independent browser demos are not this native review layout. A locally packed AIX does not change an installed resource. Import/rebuild the source/package in the existing cloud Agent before phone/glasses resource synchronization; do not replace its identity with the CLI's local development ID. Record the cloud package and actual installed version. Deployment and new-package device acceptance are still pending.

New-package device acceptance must cover: inline five labels, category beside amount, empty values, long-value scrolling, fixed bottom actions and focus; microphone permission, real transcription and ambiguous instructions; draft visibility/originals on the website; separate phone accounting consent/revocation; successful confirmation and duplicate warnings; interrupted/late requests and Agent/device restart; no repeated expenses or financial changes from Voice edit/Draft. Record actual firmware and resource-package versions when testing.

Voice feedback lists changed fields and includes the complete resulting merchant when changed. For an unchanged result, only a complete merchant-only utterance naming the exact current value, with no server warnings, gets “商户已是 SEIYU，无需修改”. An unapplied or ambiguous instruction instead asks the user to check the retained transcript, shows the current merchant (including an empty value) and preserves warnings. This display rule does not infer missing AI patches or modify candidate values. Tests cover SEIY → SEIYU, SEIYU → SEIYU and a different requested name that was not applied. Browser geometry checks verify first/final glyph bounds and long-name scroll reachability, but cannot establish the glasses runtime's rendering behavior.
